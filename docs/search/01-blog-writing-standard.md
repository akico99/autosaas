# 블로그 자동화 원고 생성 기준 v1

조사일: 2026-10-04, 한국 시간. 대상: 이 프로젝트의 네이버 블로그 검색용 원고. 홈판용은 별도 목표로 관리한다.

**결론: 현재 앱에는 주제별 대응이 있으나 키워드별 실제 검색 결과에 맞춘 설계와 내용 검증이 부족하다. 원고 생성 기준은 `주제 × 검색 의도 × 검색 결과 유형 × 보유 근거`로 정한다.** 아래는 조사에 기반한 운영 기준이며, 순위가 검증된 최적 공식은 아니다. 실제 성과로 조정해야 한다. 이번 작업은 조사·기준 수립이며 앱 코드에는 적용하지 않았다.

## 1. 현재 앱이 원고를 만드는 방식

| 단계 | 실제 구현 | 한계 |
|---|---|---|
| 용도 구분 | 홈판용과 검색용 생성 엔진·프롬프트 분리 | 검색 노출·AI 인용·홈피드 성과를 별도로 측정하는 루프는 확인되지 않음 |
| 주제 구분 | 검색 주제 32개, 문체·글 성격 A/B/C/D, 주제별 mustInclude 안내 | 분류가 실제 키워드 의도를 대신할 수 없음 |
| 의도 판단 | 자동완성, 뉴스·배경·블로그 자료를 전달하고 모델이 의도를 추론 | 해당 키워드의 통합검색 구성·블록·상위 문서 요구사항을 체계적으로 분석하지 않음 |
| 제목 | 메인어 + 자동완성 세부어 1~2개 + 정답 예고/후킹 | 자동완성 후보를 제목에 강제. 후보가 주 의도와 다르면 범위가 넓어질 수 있음 |
| 본문 | 1,800~2,500자 지시, 소제목 4개 이상, 이미지 5~10장 지시 | 수량을 채우는 것이 질문 해결보다 앞설 위험 |
| 자료 수집 | 기사 본문, 블로그 스니펫·후기, 인물 배경, 장소 정보, 입력한 공식 자료 등 | 자료 부족·수집 실패에도 생성 진행 |
| 하드 검증 | 본문 1,800자 이상, 소제목 4개 이상, 인용구 최대 2개, description 존재 | 제목·내용의 의도 일치, 근거, 주제별 필수 답변은 검증하지 않음 |
| 재생성 | 기본 최대 3회. 검증에 실패한 후보 중 본문이 더 긴 후보 보존 | 더 긴 글이 더 나은 글이라는 보장이 없음. 마지막에도 실패 후보를 반환할 수 있음 |
| 팩트 대조 | 생성 후 factCheck 결과·수집 진단 반환 | 경고이며 발행 차단은 아님 |

확인한 코드:

- `src/generator/searchTopics.js`: 주제·문체·mustInclude와 SEARCH_MIN_LENGTH=1800.
- `src/generator/buildSearchPrompt.js:73`: 검색용 시스템 프롬프트. 122행 분량, 127행 소제목, 131~133행 AI·링크 관련 단정, 135행 이미지 수량, 360~368행 자동완성 강제.
- `src/generator/generateSearchPost.js:58`: 자료 수집과 생성. 143행 팩트 대조, 339~350행 후보 선택·반환, 375행 검증 함수.
- `src/generator/generatePost.js:655`: 홈판은 자극 단어·유형별 최소 분량·본문 완결성·소제목 등을 검사. 검색용과 글자수 집계 방식도 다르다.
- `src/keyword/competition.js`: 최신순 게시물의 발행 밀도로 경쟁을 근사한다. 상위 결과의 품질·출처 경쟁력을 재는 지표는 아니다. 실패 시 gap=60, 자료 3건 미만이면 gap=82를 반환하므로 측정 실패와 기회를 분리해야 한다.

### 내용 검증이 빠진다는 재현 증거

2026-10-04에 기존 `validateSearchPost`를 직접 호출했다. 사회·정치 주제에 무관한 제목, 소제목 4개, 무관한 반복 본문, description만 제공했다. 결과는 `ok:true`, `issues:[]`, `bodyLength:3096`, `hasMustInclude:true`였다. 대상·기간·기관·신청 방법은 전혀 없었다. `hasMustInclude`는 설정의 존재 표시이며 내용 충족 여부가 아니다. 이 확인은 LLM 생성·게시·외부 API 호출 없이 검증 함수만 대상으로 했다.

## 3. 공식 근거와 현재 프롬프트에서 바로잡을 가정

[네이버 D.I.A. 설명](https://help.naver.com/service/5626/contents/22926?osType=COMMONOS)은 키워드별 선호 문서와 주제 적합성·경험·정보 충실성·의도·독창성·적시성 등을 함께 평가한다고 설명한다. 따라서 키워드마다 다른 원고 요구를 설정하는 방향이 타당하다. 공개 문서는 개별 요소의 가중치나 보장되는 글자수를 제시하지 않는다.

[네이버 C-Rank 설명](https://help.naver.com/service/5626/contents/22927?osType=COMMONOS)은 출처의 신뢰도를 평가한다고 설명한다. 원고 한 편의 형식 외에 블로그가 다루는 주제와 축적된 콘텐츠도 고려해야 한다. [블로그 고객센터](https://help.naver.com/service/5593/contents/10585)는 시중의 블로그 지수·최적화 등급을 네이버가 만든 개념으로 보지 않는다고 안내한다. 앱에서 민간 등급을 공식 점수처럼 쓰지 않는다.

[2024-02-01 스마트블록 발표](https://navercorp.com/media/pressReleasesDetail?seq=31528)는 검색 의도 세분화와 VIEW 영역 전환을 설명한다. 통합검색 내 블록 위치, 블록 안의 문서 위치, 블로그 탭 위치는 서로 구분해서 관찰해야 한다.

[콘텐츠 작성 권장 사항](https://searchadvisor.naver.com/guide/content-basic)은 경험과 전문성, 일관된 주제, 투명한 인용, 읽기 쉬운 구조, 정보 갱신을 안내한다. 뉴스 인용 시 원문 링크를 명시하고 AI 결과에 운영자의 관점을 더하라고 권장한다. 이는 웹 콘텐츠 가이드이므로 블로그의 공개 랭킹 수식으로 해석하지 않는다.

[웹 콘텐츠 스팸 사례](https://searchadvisor.naver.com/guide/content-abusing)는 키워드 남용·낚시·유사 템플릿 대량 생성·스크래핑을 구분하고, 특정 기술을 사용했다는 사실만으로 판단하지 않는다고 설명한다. 자동화의 목표는 가치 있는 초안을 만드는 것이며 문장 패턴을 바꿔 탐지를 피하는 것이 아니다.

| 기존 가정 | 새 기준 |
|---|---|
| AI로 쓴 글은 색인 제거 | AI 사용 자체로 일괄 판정하지 않음. 근거·독창적 분석·실제 경험·독자 효용을 검수 |
| 외부 링크는 검색 불이익 | 공식 신청·원문·제품 문서 등 독자의 확인과 행동에 필요한 링크 제공. 무관한 홍보·링크 남용과 구분 |
| 1,800자·소제목 4개·사진 5~10장이 상위노출 조건 | 기존 앱의 제작 규칙으로 표시. 검색 질문에 답하는 데 필요한 분량·구조·증거로 대체 |
| 자동완성은 모두 본문 소재 | 의도가 같은 후보만 선택. 다른 목적의 후보는 다른 원고로 분리 |
| 짧은 키워드는 최신 뉴스 맥락 하나를 강제 선택 | 뉴스성·상시 정보성·브랜드 탐색을 먼저 구분. 대상이 모호하고 근거가 부족하면 초안 보류 |
| 타인의 후기를 바탕으로 내돈내산 문체 | 직접 사용·방문 기록이 없으면 자료 기반 소개/비교로 전환. 타인의 경험은 출처와 함께 타인의 것으로 전달 |
| 오래 읽히면 무조건 순위 상승 | 필요한 답을 빨리 제공. 체류 지표의 개별 가중치를 공개 사실처럼 단정하지 않음 |

## 4. 앞으로 사용할 생성 절차

`키워드 입력 → 결과 조사 → 의도·대상 확정 → 근거 수집 → 원고 기획 → 생성 → 내용 검증 → 사람 검수 → 발행 후 평가`

### A. 키워드별 기획서부터 만든다

원고마다 다음 항목을 먼저 채운다. 32개 주제는 유지하되 검색 의도는 별도 축으로 관리한다.

| 항목 | 기록 내용 |
|---|---|
| 대상 | 정확한 제품 모델·사람·서비스·지역·제도·용어. 동명이인과 다른 뜻 구분 |
| 주 의도 | 정의/설명, 방법/절차, 비교/선택, 경험/후기, 장소/방문, 최신 이슈, 서비스/공식 사이트 찾기 |
| 핵심 질문 | 독자가 이 글에서 반드시 해결해야 하는 질문 1개 |
| 관련 질문 | 같은 목적에 딸린 필요한 질문만 추가. 질문 수는 주제별로 조정 |
| 결과 환경 | 검색어, 수집 시각(KST), 기기·로그인 조건, 실제 노출 영역·블록, 광고 여부 |
| 관찰 문서 | 같은 의도의 비광고 문서에서 제목·날짜·질문 범위·근거·누락 사항 기록 |
| 자료 | 직접 읽은 원문 URL·발행일·확인일·적용일, 직접 경험 입력, 사진 및 사용 근거 |
| 추가 가치 | 내 자료·계산·실험·조건별 비교·새로운 설명 중 무엇을 제공할지 |
| 보류 조건 | 중요한 자료 부족, 사실 충돌, 모호한 대상, 직접 경험 없는 후기 요청 등 |

기본 조사 표본은 같은 의도의 비광고 문서 5~10개를 목표로 한다. 이는 운영상 표본 제안이며 네이버 공식 기준이 아니다. 결과가 적으면 실제 수만 기록한다. 스니펫만 읽고 본문을 읽었다고 표시하지 않는다. 상위에 있다는 사실은 정확성을 증명하지 않으므로 사실은 원자료에서 확인한다.

자료를 못 가져오면 `자료 부족/수집 실패`로 표시한다. 검색량·경쟁력·성공 확률을 임의로 채우지 않는다. 최근 게시물 수는 발행 활동 지표로만 사용한다. 검색광고의 광고 경쟁 정보도 자연 검색 난이도로 치환하지 않는다.

### B. 검색 의도별 필수 답변

아래 요구사항 중 해당 키워드에 필요한 것을 기획서에서 선택한다. 모든 글에 모든 항목을 넣지 않는다.

| 의도 | 반드시 해결할 내용 | 적합한 근거·구성 | 보류·전환 조건 |
|---|---|---|---|
| 정의·개념 | 의미, 구성, 예시, 헷갈리는 개념과 차이 | 신뢰할 수 있는 원전/사전/기관, 쉬운 설명·비교 | 검색 대상의 뜻이 불명확 |
| 방법·절차 | 대상, 준비물, 실제 순서, 비용·시간, 예외·실패 시 조치 | 공식 안내, 확인한 화면, 실행 조건과 단계 | 신청·결제 등 핵심 행동 안내의 근거 미확인 |
| 비교·추천 | 동일 기준의 차이, 비용 범위, 용도별 선택, 한계 | 모델/버전/기간을 맞춘 자료·비교표 | 다른 조건의 수치 혼합, 추천 근거 부족 |
| 실사용·방문 후기 | 작성자가 언제 무엇을 경험했는지, 장단점, 당시 조건 | 사용자 제공 경험 기록·실사진·구매/방문 정보 | 경험 없으면 자료 기반 소개로 전환. 내돈내산 표현 금지 |
| 장소·여행 | 위치·접근, 운영일·시간, 비용, 예약·주차·동선 중 필요한 것 | 공식 장소 정보 + 시점이 명확한 실제 방문 기록 | 후기의 시점이 불분명하거나 지점 혼동 |
| 최신 이슈 | 무엇이 언제 발생했는지, 확인된 상태, 관련 배경, 미확인 내용 구분 | 공식 발표 우선, 기사 원문 교차 확인 | 추측·소문밖에 없거나 동명이인 충돌 |
| 서비스·공식 사이트 찾기 | 운영 주체, 접근 방법, 무료/유료 범위, 확인 가능한 기능 | 실제 공식 페이지, 요금·약관·사용 화면 | 기능·가격 미확인, 공식 서비스로 오인시킬 표현 |

건강·금융·법·정책처럼 오류 영향이 큰 원고는 필요한 최신 전문기관·공식 자료를 확보하고 검수한다. 완곡한 표현이나 면책문만 넣어 근거 부족을 해결했다고 보지 않는다.

### C. 본문 공통 기준

1. **한 원고의 주 질문을 분명히 한다.** 서로 다른 검색 의도를 전부 넣지 않는다. 주 질문의 해결에 필요한 관련 질문은 함께 다룬다.
2. **제목은 대상 + 실제 질문/해결 범위를 정확히 표현한다.** 자동완성이나 후킹을 의무로 붙이지 않는다. 숫자는 실제 내용과 맞을 때만 사용한다.
3. **도입에서 답과 적용 조건을 먼저 제공한다.** 긴 공감 서론으로 답을 늦추지 않는다. 날짜·대상·예외가 있으면 답과 함께 쓴다.
4. **문단마다 새 정보가 있어야 한다.** 소제목·표·Q&A는 정보 전달에 필요할 때 사용한다. Q&A는 본문을 그대로 반복하지 않는다.
5. **길이는 필요한 답을 완성하는 만큼 정한다.** 상위 표본의 분량은 참고로 기록하되 평균 길이를 성공 원인으로 해석하지 않는다. 짧은 정의와 상세 신청 안내를 같은 길이로 맞추지 않는다.
6. **사진은 정보의 증거 또는 이해를 돕는 용도로 쓴다.** 장수를 채우기 위한 소품·무관한 인물 이미지를 넣지 않는다. 직접 경험의 사진과 참고 이미지를 구분한다. 공식 이미지도 사용 조건을 확인한다.
7. **근거 없는 경험·수치·평점·가격·발언·효능을 생성하지 않는다.** 핵심 사실은 출처 URL과 시점을 보존한다. 불확실한 핵심 답은 삭제하거나 보류한다.
8. **작성자의 추가 가치를 요구한다.** 단순 요약을 넘어 직접 기록, 조건별 사례, 투명한 계산, 비교, 오류 해결 과정을 제공한다. 실제 경험이 없어도 근거 있는 고유 분석은 가능하다.
9. **행동 안내를 막지 않는다.** 공식 신청·원문 등 필요한 링크를 제공하고 광고·제휴 관계를 정확히 표시한다. CTA는 독자의 목적을 돕는 수준으로 배치한다.
10. **검색용·홈판용·AI 인용 성과를 분리한다.** 홈판의 자극 단어를 검색용 기준으로 이식하지 않는다. AI 인용을 유일한 검색 성과로 보지 않는다.

## 5. 사주 키워드에 적용하는 예

실제 확인한 검색은 `사주 뜻`과 `사주 궁합` 두 개다. Chrome의 현재 세션에서 관찰한 표본이며 PC 환경의 결과다. 비로그인 기준이나 모든 사용자에게 동일한 결과라고 주장하지 않는다. 아래 나머지 키워드는 설계 예이며 검색량·난이도·상위노출을 검증한 목록이 아니다.

| 키워드 | 의도 | 원고 범위·제목 예 | 근거 |
|---|---|---|---|
| 사주 뜻 | 개념 설명 | 사주 뜻과 사주팔자 차이: 네 기둥·여덟 글자를 예로 설명 | 사전·명리 개념 자료. 뉴스·서비스 광고 중심으로 쓰지 않음 |
| 사주 궁합 | 혼합 의도 | 먼저 결과에서 설명·상담 후기·서비스 탐색을 구분. 설명형이면 `사주 궁합 보는 기준과 띠 궁합의 차이`처럼 범위를 좁힘 | 해석 체계의 출처·한계. 관계 결과를 확정하지 않음 |
| 사주 보는 법 | 방법 설명 | 만세력에서 무엇부터 확인하는지, 입력 조건과 읽는 순서 | 명리 자료·확인한 도구 사용 과정 |
| 무료 사주 사이트 | 서비스 비교 | 무료로 제공하는 범위, 추가 결제 단계, 이용 조건 | 직접 확인한 공식 서비스·요금 페이지 |
| 온라인 사주 후기 | 직접 사용 후기 | 사용한 서비스, 이용일, 받은 결과와 평가의 이유 | 사용자 제공 실제 사용 기록. 기록 없으면 소개형으로 전환 |
| 궁합 안 좋으면 | 불안·해석 이해 | 풀이가 달라지는 이유·해석의 한계·현실적 관계 판단 | 명리 해석과 현실의 사실을 구분. 파국·이별을 단정하지 않음 |

관찰한 결과:

- [사주 뜻](https://search.naver.com/search.naver?query=%EC%82%AC%EC%A3%BC%20%EB%9C%BB): 상단에 국어사전과 AI 브리핑 영역이 나타났다. 개념 질문은 검색 결과에서 바로 해결될 가능성이 있어 클릭 감소 가능성을 고려해야 한다. 이는 성과 측정 전 가설이다.
- [사주 궁합](https://search.naver.com/search.naver?query=%EC%82%AC%EC%A3%BC%20%EA%B6%81%ED%95%A9): 광고·브랜드 콘텐츠와 비광고 설명 글·후기·지식iN·서비스 결과가 함께 나타났다. 설명 문서와 상담 판매 문서를 하나의 순위 경쟁으로 묶어 평가하면 안 된다.

## 6. 원고 통과 기준

`형식 통과`와 `내용 통과`, `발행 준비 완료`를 구분한다. 아래는 앱에 추가할 운영 기준이다. 아직 구현되지 않았다.

### 내용 검사

- 주 질문과 제목·도입·본문이 일치한다.
- 기획서의 필수 답변을 모두 다룬다. 항목별로 해당 본문 블록과 근거를 연결한다.
- 수치·기간·가격·고유명사·주요 주장에는 확인 가능한 자료가 있다.
- 사실 충돌·자료 누락·수집 실패가 숨겨져 있지 않다.
- 직접 경험을 주장한 경우 사용자 입력이 뒷받침한다.
- 기존 글·다른 자료를 기계적으로 반복하지 않고 추가 가치가 있다.
- 독자가 실제 다음 행동을 할 수 있다. 중요한 링크·조건·예외가 정확하다.

모델에게 항목별 충족 여부와 근거 블록을 판정하게 하되, 모델 점수만으로 사실 확인을 대신하지 않는다. 제목·URL·날짜·가격 일치 같은 결정적 검사는 코드로 보조한다. 임의의 100점 평가를 네이버 랭킹 점수처럼 표시하지 않는다.

### 보류 조건

중요한 사실이 근거와 충돌하거나, 핵심 질문에 답할 자료가 없거나, 허위 방문/실사용을 요구하거나, 대상이 불명확하면 생성 또는 발행 준비를 보류한다. 일반적인 편집 개선은 경고로 구분한다. 재시도 후에도 실패한 후보는 길이가 길다는 이유로 준비 완료 처리하지 않는다.

## 7. 키워드마다 달라지는 기준을 유지하는 대책

**결과 조사와 발행 후 성과를 함께 기록한다.** 검색 결과 관찰만으로 순위 원인을 알아냈다고 할 수 없다.

### 측정 항목

| 항목 | 기록 원칙 |
|---|---|
| 검색 노출 관찰 | 검색어·시각·기기·로그인 조건·영역·블록명·관찰한 문서 위치·URL |
| 결과 없음 | 관찰한 범위 밖이면 `관찰 범위 내 미노출`. 수집 실패는 `측정 실패`. 두 상태를 분리 |
| 검색 유입 | 블로그 통계에서 실제 제공되는 검색 유입·유입어만 기록 |
| 독자 반응 | 이용 가능한 체류·조회·클릭 등을 기록. 제공되지 않는 노출수·CTR을 만들지 않음 |
| 목표 행동 | 추적 가능한 공식 이동·상담·구매 등. 추가 가치와 유입 품질을 함께 평가 |
| AI 인용 | 브리핑이 생성됐는지와 해당 글 인용 여부를 구분. 브리핑 미생성은 인용 실패로 처리하지 않음 |
| 문서 변경 | 생성 기준 버전·발행일·수정일·수정 내용. 같은 URL의 전후 비교에 사용 |

독립 사이트의 Search Console/서치어드바이저 기능을 네이버 블로그에도 그대로 이용할 수 있다고 가정하지 않는다. 관찰 순위는 개인화·지역·기기·경쟁 글 변경의 영향을 받으므로 절대 순위로 표시하지 않는다.

### 초기 평가 운영안

발행 후 1·3·7·14·28일에 확인하는 일정을 제안한다. 이는 점검 일정이며 해당 기간에 색인·순위가 확정된다는 뜻이 아니다. 이번 작업에서 예약·자동 모니터는 생성하지 않았다.

처음에는 실제 보유 자료가 있는 한 주제에서 12~20개의 서로 다른 질의를 대상으로 소규모 평가한다. 유사한 의도·경쟁 환경의 키워드를 묶어 기존 구조와 새 구조를 비교하되, 두 방식 모두 사실성·허위 경험 금지 기준을 지킨다. 동일 키워드에 유사 글을 여러 개 발행해 서로 경쟁시키지 않는다. 한 번에 많은 변수를 바꾸면 원인을 구분하기 어려우므로 제목 범위·첫 답변·내용 충실성 중 변경 항목을 기록한다.

주별로 의도 유형별 검색 유입과 목표 행동을 비교한다. 표본이 작거나 계절·이슈 변화가 크면 인과관계를 확정하지 않는다. 부진하면 실제 검색 결과에서 의도와 경쟁을 다시 확인하고, 새 글의 무의미한 양산보다 기존 글의 자료·답변을 보완한다.

## 8. 앱 개선 우선순위

| 우선순위 | 변경 | 관련 위치 | 완료 판단 |
|---|---|---|---|
| P0 | 외부 링크·AI 일괄 배제·수량과 순위의 인과 단정 정비 | buildSearchPrompt.js, searchTopics.js | 프롬프트가 확인된 사실과 제작 제안을 구분 |
| P0 | 허위 경험 방지와 중요한 근거 충돌 시 보류 | buildSearchPrompt.js, generateSearchPost.js, factCheck.js 및 발행 경로 | 직접 경험 없는 내돈내산 원고와 근거 실패 원고가 준비 완료 상태로 진행되지 않음 |
| P1 | 키워드별 결과·의도·질문·근거 기획서 추가 | 새 조사 모듈과 검색용 생성 경로 | 같은 주제라도 정의/절차/후기를 구분하고 근거 부족 상태를 표시 |
| P1 | mustInclude 내용 검사와 후보 선택 개선 | generateSearchPost.js | 위 반복문 재현이 내용 검사에서 실패. 긴 후보보다 필수 답변·근거 충족 후보 우선 |
| P1 | 분량·소제목·이미지 수량을 의도별 편집 기준으로 변경 | buildSearchPrompt.js, searchTopics.js, 검증·UI 경로 | 간단한 개념 설명을 불필요하게 늘리지 않고 복잡한 절차를 빠뜨리지 않음 |
| P2 | 성과 기록과 기준 버전 관리 | 저장·통계·점검 경로 | 측정 실패/미노출을 구분하고 의도 유형별 개선 전후 확인 가능 |

세부 코드 설계·구현·전체 앱 검증은 후속 작업이다. 이 문서는 현재 상태를 평가하고 사용할 기준을 확립한 결과물이다.
