# 여행커넥트 구현 결정 기록

사용자 요청에 따라 기존 앱을 확장하며 결정한 범위다. 설계 시점은 2026-10-07~08이다. 실제 구현·검증 상태는 STATUS와 구현 계획에 기록한다.

| 결정 | 이유 | 전제가 틀릴 때의 영향 |
|---|---|---|
| 검색용 여행 블로그부터 구현, 홈판·SNS·쇼핑 전용 탭 후속 | SNS 후순위와 기존 앱 기반 요청 | 홈판 유입이 우선이면 별도 기획·사진·경험 흐름 필요 |
| 실제 발급 상품 대신 합성 자료로 개발 검증 | 실제 상품·발급 링크가 제공되지 않음 | 실상품 조건·사용권·실계정 동작을 추가 검증해야 함 |
| 격리 작업 공간에서 현재 사용자 변경을 기준으로 개발 | 다른 작업과 기존 예약·보관 기능 보존 | 적용 직전 추가 변경과 충돌하면 재통합 필요 |
| 사용자 요청에 따라 단계별 작업자와 독립 검토 사용 | 고성능 작업과 반복 구현 역할 분리 | 단계별 검토 시간과 호출 비용 증가 |
| 여행 작성 기본값 Opus, 기존 1차 검사 Haiku, 반복 검사 코드 | 사용자의 모델 역할 분리 요청 | 작성 비용 증가, Haiku의 사실 판정은 사람 검수 필요 |
| 상품 등록은 사용자 출처·발췌를 검토해 시작 | 공급사별 자동 추출과 공식 연동이 확인되지 않음 | 등록 수작업 필요, 자동 탐색은 후속 개발 |
| 사용자 발췌와 상세 원문 접근 수준을 구분, 검색 스니펫은 검토 사실 근거로 승격하지 않음 | 근거 신뢰도 보존 | 충분한 원문이 없으면 원고 보류 또는 검수 항목 증가 |
| 첫 가격 입력은 KRW | 최소 통화 단위와 발췌 숫자 대조를 명확하게 검증 | 외화 옵션은 환산·소수점 검증 확장 필요 |
| 표·FAQ·본문의 가격과 날짜·객실은 상품/옵션 단위 검사 | 다른 옵션의 금액을 잘못 승인하지 않기 위함 | 옵션이 모호한 비교표가 보류될 수 있음 |
| 가격 확인 24시간 이상·누락·미래 시점은 hold | 전송 직전 가격 근거의 신선도 확보. 네이버 정책 기간이 아닌 앱 운영값 | 사용자가 가격을 더 자주 재확인해야 함 |
| 같은 조건의 확인 시각 갱신은 허용, 금액·옵션·링크 변경은 이전 원고 보류 | 오래 보관한 원고와 현재 상품 대조 | 조건이 바뀌면 원고 수정·재검수 필요 |
| 직접 경험은 전용 경험 입력에서만 사용 | 뉴스·타인 후기·일반 메모를 작성자 체험으로 만들지 않음 | 실제 경험도 전용 입력이 없으면 정보·비교형으로 제한 |
| renderer의 상품 맥락·정책을 믿지 않고 main이 등록 자료로 재구성 | 생성·수정·전달의 동일한 검수 기준 | 새로운 정책 입력은 서버 계약 변경 필요 |
| 국내/해외 여행은 검증된 travelTopic enum으로 직접 선택 가능 | 목적지 정규식만으로 모든 지역·혼합 상품을 분류하기 어려움 | 사용자가 잘못 선택하면 글의 기획 방향이 맞지 않을 수 있음 |
| review 원고는 사유 표시 후 명시적 사람 검수 전달 가능, hold는 차단 | 검수 필요와 전달 금지 구분 | 사람이 검수 항목을 놓칠 위험은 남음 |
| 단일 생성은 기존 보관함에 한 번 저장, 배치·가져오기 중복 저장 안 함 | 저장 원고 id를 기준으로 전달 검사 | 공용 보관함 용량 제한이 생성에 영향을 줌 |
| 공용 보관함 200개에서 새 여행 원고 저장 거부 | 기존 사주 원고를 자동 삭제하지 않음 | 사용자가 보관함을 정리해야 함 |
| 가져온 원고는 불완전한 등록 상태에서도 본문을 보관, 링크·고지 자동 복구 금지 | 작성한 글 보존과 잘못된 링크 수정의 은폐 방지 | 직접 수정 전 전달이 보류됨 |
| 여행 사진·상태는 패널 안에서 보관, 실제 전달 중 공용 상태를 임시 변경하고 복원 | 탭 전환과 지연 작업의 상태 혼입 방지 | 공용 에디터 구조를 바꾸면 통합 검증이 다시 필요 |
| 여행 마운트 컨테이너는 레이아웃을 만들지 않고 내부 패널을 기존 flex 영역에 배치 | 내용이 창 밖으로 늘어나 스크롤이 사라지는 문제 수정 | 화면 검사는 실제 앱 CSS·분할 패널 구조와 기본·최소 창 크기를 함께 사용 |
| 에디터 대상은 현재 오른쪽 블로그, 프로필이 계정을 자동 전환하지 않음 | 실제 로그인 상태와 콘텐츠 프로필 구분 | 사용자가 대상 블로그를 직접 확인해야 함 |
| 기존 새 글쓰기 준비·strictInject·성공 확인 재사용 | 쓰던 글 보존과 기존 기능 회귀 방지 | 네이버 화면 변경 시 별도 실계정 검증 필요 |
| 사진 처리·새 글쓰기 준비 후에도 저장 원고 id로 서버 재검사 | 기다리는 동안 가격 시점·상품·원고가 바뀌는 경우 차단 | 추가 로컬 읽기와 검수 대기가 발생함 |
| 명시적 여행커넥트 전달에서는 구버전의 내돈내산·추가 고지·자동 관련글 삽입을 적용하지 않음 | 최종 검수 이후 잘못된 고지나 미등록 URL이 붙는 문제 방지 | 여행 원고의 자동 관련글 안내는 별도 설계 필요 |
| 직접 경험·사진 사용권·실상품 대조는 합성 테스트로 완료 처리하지 않음 | 오프라인 개발 검증의 범위 명시 | 운영 전 사람의 실자료 검토 필요 |
| Sonnet 작업자의 429 발생 후 native Luna 작업자로 반복 구현 대체 | 반복 재시도 없이 진행 | 개발 모델 구성은 원래 배정과 달라짐; 앱의 Opus/Haiku 역할은 유지 |

메인 연결과 보관함 통합은 같은 파일의 동시 수정을 피하기 위해 UI 단계의 backend 작업에서 먼저 구현했다. 생성 결과에는 전체 상품 맥락을 보존하고 부가 기획 정보만 덧붙였다. 옵션 사실의 권장 필드는 `variant:<id>:price`, `variant:<id>:departureDate`, `variant:<id>:roomBasis`이며, 과거 공용 날짜·객실 사실은 같은 값이 확인된 경우에만 호환한다.
