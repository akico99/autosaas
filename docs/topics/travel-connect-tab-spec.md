# 네이버 여행커넥트 전용 탭 — 조사 및 설계안

작성·확인 기준: 2026-10-07 KST. 상태: 구현 검토용 설계안. 이번 작업은 조사와 계획 작성이며 제품 코드는 구현하지 않았다.

## 1. 목적과 권장 방식

기존 blog-auto에 `여행커넥트` 탭을 추가한다. 제휴 가능한 여행 상품을 등록하고, 독자의 예약 고민에 맞는 키워드를 선정해 **네이버 블로그 원고 1편**을 만든다. 2026-10-07 후속 요청에 따라 **SNS 문안 생성·SNS 자동 수집은 후순위**로 옮긴다. 아래 SNS 관련 상세 설계는 후속 확장 참고이며 1차 구현·공수·완료 기준에 포함하지 않는다.

이번 수정의 우선 원칙은 현재 앱에 기능을 붙이는 것이다. 키워드 조사, `generateSearchPost`, 검색 브리프·팩트 대조, 주제 프로필, 원고 보관함, 이미지 배정, 에디터 전달, 블로그 성과 기록을 재사용한다. 별도 블로그 생성 엔진·원고 보관함·성과 저장소를 다시 만들지 않는다. 여행 상품 조건·제휴 종류·원문 링크 보존·추가 검수에 필요한 모듈만 추가한다.

여행과 쇼핑은 `상품 탐색 → 키워드 선정 → 상품 근거 확인 → 원고 생성 → 고지/링크 → 검수/보관 → 성과`라는 제작 흐름을 공유한다. 공통 제휴 맥락은 `connectKind:'travel'|'shopping'`으로 구분하며 여행 일정/가격 조건과 쇼핑 스펙/배송 조건은 각각의 상품 상세 필드로 둔다. **첫 구현은 검색용 여행 블로그이며 쇼핑 전용 탭 추가는 이 비교만으로 구현 범위에 자동 포함하지 않는다.**

| 공통으로 재사용할 것 | 여행에서 구별할 것 | 쇼핑에서 구별할 것 |
|---|---|---|
| 키워드·상품 매칭, 원문 근거, 원고·이미지·보관함·에디터 | 출발일·인원·객실·포함/불포함·팁·선택관광·취소 | 모델·옵션·용량·수량·호환성·배송비·반품 |
| 고지·발급 링크 원문 보존·제휴 적합성 | 여행 고지: 예약 발생 시 수수료 | 쇼핑 고지: 판매 발생 시 수수료 |
| 공식 실적 기록과 확정/예상 구별 | 24시간 이내 예약·최근 클릭 기준 | 직접/간접 실적·유입 24시간·집계 7일·우선순위 |

쇼핑 실적 규칙은 여행과 다르므로 동일 계산식을 재사용하지 않는다. 쇼핑 직접 실적은 상품별 수수료, 간접 실적은 기본 수수료와 예외를 공식 자료에서 확인해야 한다. [쇼핑 실적 인정 기준](https://help.naver.com/service/30027/contents/24106?osType=COMMONOS), [쇼핑 고지·링크 안내](https://help.naver.com/service/30027/contents/24104?osType=COMMONOS)

노출 목표는 검색이다. 지역·동행 대상·여행 형태·예약 전 확인 질문을 제목과 필수 답변에 반영한다. 홈판용 경험·사진 중심 원고는 후속 범위이며, 실제 경험 입력 없이 체험담을 만들지 않는다. 여행 기획·작성은 기존 SDK의 Opus 모델, 1차 내용 대조는 기존 Haiku, 링크·고지·스냅샷·가격 확인 시점 검사는 결정적인 코드 규칙으로 나눈다.

성공 기준은 생성 건수보다 상품 조건의 정확성, 원고의 질문 해결력, 검수 시간, 실제 예약 실적이다. 검색 상위 노출·수익·SNS 도달을 보장하는 기능으로 설명하지 않는다.

권장 방식은 **상품과 키워드를 왕복하는 반자동 제작 흐름**이다. 상품을 먼저 등록해 발급 가능한 제휴 링크를 확보하고, 상품의 지역·일정·대상에 맞는 키워드를 찾는다. 별도로 발견한 질문도 기존 상품과 매칭한다. 상품 없이 키워드만 있는 후보는 조사 후보로 보관한다.

| 접근 | 장점 | 제약 | 결정 |
|---|---|---|---|
| 상품 등록 → 키워드 추천 → 근거 확인 → 원고 생성 | 판매 가능한 상품과 글감의 연결이 명확하고, 계정·수집 제약에 대응하기 쉽다 | 최초 상품 등록은 사람이 한다 | 1차 권장 |
| 키워드·SNS 질문 → 상품 자동 검색 → 원고 생성 | 새로운 수요와 틈새 질문을 찾기 좋다 | 공식 상품 접근 방법·API와 SNS 권한 확인이 필요하다 | 2차 확대 |
| 전체 상품·SNS 상시 수집 → 대량 생성·발행 | 수집 범위가 넓다 | 비용·차단·오래된 가격·중복 글·계정 접근 문제를 먼저 해결해야 한다 | 초기 범위 제외 |

### 2.3 Threads·X 조사 결과와 제약

- Threads·X에서 `여행커넥트`, `여행 커넥트`, 일본 패키지·부모님 여행 등의 공개 웹 색인 검색을 시도했다. 이 계획의 근거로 쓸 만한 직접 게시물을 확보하지 못했다. 확인하지 못한 전문가 게시물·수익 인증·알고리즘 비법을 인용하지 않는다.
- Threads 개발자 문서의 키워드 검색·게시 문서 요청은 429로 제한됐다. **API로 전체 공개 게시물 또는 댓글을 수집할 수 있다는 전제는 두지 않는다.** 연결 단계에서 실제 권한, 검색 범위, 보존 규칙을 확인한다.
- X 공식 검색 API는 최근 7일 검색과 전체 기간 검색을 구분한다. 개발자 앱·토큰·비용·한도를 확인한 뒤 2차 수집 옵션으로 연결한다. API 지원과 무료 이용은 같은 뜻이 아니다. [X 검색 문서](https://docs.x.com/x-api/posts/search/introduction)
- Threads는 짧은 본문 500자 프로파일로 시작한다. 별도 긴 텍스트 첨부 기능은 존재하지만 첫 버전에서 사용하지 않는다. [Meta 기본 게시물 안내](https://about.fb.com/news/2023/07/introducing-threads-new-app-text-sharing/), [긴 텍스트 첨부 안내](https://about.fb.com/news/2025/09/attach-text-threads-posts-share-longer-perspectives/)
- X 기본 문안은 가중 길이 280 이내로 검증한다. 한글·이모지·URL 처리 때문에 JavaScript `text.length`를 그대로 쓰지 않는다. 공식 문서에서 권장하는 `twitter-text`를 사용한다. [X 글자 수 문서](https://docs.x.com/fundamentals/counting-characters)

따라서 첫 버전은 공개 검색·사용자가 입력한 URL/발췌를 이용한 **조사함**을 제공한다. 검색 결과와 사용자가 제공한 발췌도 접근 수준을 표시한다. SNS API 자동 수집은 범위가 검증된 뒤 추가한다.

### 2.4 사실과 설계 가설의 구별

공식 상품 조건·정책은 출처와 날짜를 가진 사실이다. 커뮤니티 질문은 독자 고민의 사례다. 아래 키워드 우선순위, 콘텐츠 구성, 갱신 주기, 개발 공수는 **제품 설계 제안**이다. 검증된 네이버 순위 공식이나 SNS 알고리즘의 규칙으로 소개하지 않는다.

## 3. 탭과 사용 흐름

상단 주제 줄에 `[사주보는 수달] [여행커넥트] [무주스키샵 준비 중] [구버전]`을 배치한다. 기본 시작 탭은 기존 설정을 보존한다.

여행 탭 내부에는 여섯 단계와 검토할 데이터가 보인다.

| 단계 | 사용자 조작 | 결과 |
|---|---|---|
| ① 기본 설정 | 블로그 프로필, 지역, 독자층, 여행 월, 출발 공항, 글 유형 선택 | 여행 전용 설정 |
| ② 상품함 | 공식 상품 찾기 열기, 상세 URL·발급 링크 등록, 조건 원문 붙여넣기 | 출처를 가진 상품 카드 |
| ③ 키워드·질문 | 검색광고 XLSX 가져오기, 자동완성·커뮤니티 자료 확인 | 키워드 후보·상품 매칭·추천 이유 |
| ④ 기획 | 주 키워드 1개, 상품 1~3개, 질문 3~5개 선택 | 공통 원고 브리프 |
| ⑤ 생성·검수 | 기존 검색 원고 생성기로 블로그 생성, 근거와 가격 확인 | ready/review/hold |
| ⑥ 보관·성과 | 원고 수정·복사·에디터 넣기, 발행 URL·실적 연결 | 버전 보관과 성과 기록 |

화면에는 `가격 확인 시점`, `출발일·인원 조건`, `자료 확인 필요`, `제휴 링크 등록 여부`를 상품 카드에서 바로 표시한다. 작은 단계 버튼을 이동해도 입력·선정 상태가 유지된다. 오류가 발생한 단계만 재시도할 수 있다.

상품 링크가 없으면 제휴 완료 원고로 내보내지 않고 정보성 초안으로 보관한다. 정책을 확인하지 못한 SNS 채널에는 제휴 링크를 자동 삽입하지 않는다. 해당 SNS 문안은 블로그 소개형으로도 생성할 수 있으며 여행 상품 홍보 문안에는 경제적 이해관계 고지를 유지한다.

## 4. 키워드 선정 방법

### 4.1 후보 생성

후보의 축은 `지역 × 독자 × 문제 × 상품유형 × 시기 × 출발조건`이다.

- 지역: 후쿠오카·오사카·다낭·제주 등 **실제 등록 상품의 지역**.
- 독자: 부모님 동반, 아이 동반, 첫 해외여행, 커플 등 사용자가 선택한 대상.
- 문제: 자유여행과 패키지 비교, 노쇼핑, 선택관광, 공항 픽업, 이동 시간, 취소 조건.
- 유형: 국내패키지·해외패키지·가이드투어.
- 시기: 실제 상품 출발일·판매 일정과 맞는 월·연휴. 지난 시기를 자동 갱신해 현재 판매처럼 표현하지 않음.

예시 후보는 `부모님 후쿠오카 패키지`, `다낭 패키지 선택관광 비용`, `오사카 근교 버스투어 아이 동반`이다. 이 예시는 검색량이 검증된 추천 목록이 아니다.

입력 자료는 네이버 검색광고 XLSX, 공개 자동완성, 검색 결과 관찰, 공식 여행 정보, 커뮤니티·SNS 질문이다. 기존 XLSX 파서를 재사용하되 현재 사주 중심 분류·씨앗 직접 포함 규칙은 여행 전용 분류로 대체한다. 띄어쓰기 정규화와 지역 별칭은 명시적인 사전으로 관리한다. 의미가 같다는 이유만으로 검색량을 합산하지 않는다.

### 4.2 선정과 점수

먼저 무관 지역·상품 미매칭·판매 종료·인정 제외 유형을 걸러낸다. 정렬은 다음 순서다.

1. 독자 조건과 상품의 적합성.
2. 상품 조건을 확인할 근거의 충분성.
3. 예약 전에 해결해야 할 질문의 구체성.
4. 블로그가 진입할 문서 영역이 관찰되는지, 기존 글이 답하지 못한 질문이 있는지.
5. 출발 일정과 현재 검색 수요의 시기 적합성.
6. 실제로 확인된 검색량과 SNS 질문 사례.

초기에는 확률처럼 보이는 총점 대신 `적합/조건부/부적합`과 항목별 `관찰됨/자료 없음`을 표시한다. 순위는 명시적인 조건의 사전식 정렬로 구현한다. 반응 수가 높다는 이유만으로 구매 의도가 높다고 판정하지 않는다.

월검색량은 공식 XLSX 값만 쓴다. `<10`과 결측을 보존하고 PC·모바일이 모두 숫자일 때만 합계를 만든다. 광고 경쟁지수는 광고 지표로만 표기한다. 자연 검색 난이도·상위 노출 가능성으로 바꾸지 않는다. SERP 수집 실패도 낮은 경쟁으로 해석하지 않는다.

### 4.3 조사함과 질문 추출

첫 버전은 자료를 직접 등록하고 검색 링크를 열 수 있는 조사함을 제공한다. 자동 수집은 허용된 공개 페이지에 한정한다. 네이버 카페 가입·회원 전용 게시물 접근을 필요 조건으로 만들지 않는다.

| 조사 출처 | 추출 대상 | 처리 |
|---|---|---|
| Threads | 짧은 고민·반응·질문 표현 | URL/발췌 등록 우선, API 범위 확인 뒤 자동화 |
| X | 최근 여행 이슈·가격 변화 질문·행사 언급 | URL/발췌 등록, 2차 공식 검색 API |
| 네이버 여행 카페·지역 카페 | 일정·가족 동반·픽업·준비물 질문 | 공개/사용자 제공 자료만, 현재 상품 조건은 공식 검증 |
| 뽐뿌·클리앙 등 공개 게시판 | 특가 조건·추가 비용·선택관광 질문 | 광고성·재게시·오래된 특가 표식 |
| Reddit 여행 커뮤니티 | 이동·접근성·투어 운영 관련 질문 | 국가·언어별 수요를 구분 |

각 자료는 `platform, url, accessLevel, publishedAt|null, collectedAt, excerpt, commercialSignal, audience, tags`를 저장한다. `accessLevel`은 `full-page / search-snippet / user-excerpt` 중 하나다. 발췌는 800자 이내로 기본 제한한다. 재게시·동일 URL을 중복 제거하고, 여러 자료에서 같은 질문이 나왔다는 것을 전체 시장 통계로 표시하지 않는다.

추출 결과는 `question, sourceIds, audience, region, planningStage, verificationNeeds`다. SNS 주장으로 상품 사실을 채우지 않는다. 개인 경험을 글쓴이의 경험으로 옮기지 않는다. 사진·문장을 그대로 재사용하지 않는다.

## 5. 상품 정보 탐색과 사실 관리

### 5.1 도입 순서

1차는 공식 상품 찾기·Chrome 크리에이터 도구를 외부 브라우저로 열어 사용자가 상품을 선택하고 링크를 발급한다. 앱에는 `상세 URL + 발급 링크 원문 + 상품 조건 원문`을 등록한다. Electron 웹뷰가 Chrome 확장 프로그램을 사용할 수 있다고 가정하지 않는다.

2차는 공급사별 공개 상세페이지 어댑터와 사용자 세션에서 현재 보고 있는 페이지의 저장 기능을 검토한다. 이번 조사에서 여행커넥트 상품 목록·링크 발급용 공개 API를 확인하지 못했으므로 이를 전제로 개발 일정을 잡지 않는다. 공식 계약·문서가 확보되면 어댑터를 추가한다.

### 5.2 필수 구조

상품 하나가 아니라 **상품 + 선택 출발일·옵션·인원**을 가격 비교 단위로 삼는다.

| 구분 | 저장할 값 |
|---|---|
| 식별 | 내부 id, 공급사, 공급사 상품 id(알 때), 이름, 유형, 국가·지역 |
| 링크 | 상세 URL, `affiliateUrlRaw`, 발급 계정/프로필 id, 발급·검증 시각 |
| 적합성 | 제휴 가능 여부와 확인 근거, 대상 독자, 출발 공항·지역 |
| 일정 | 출발일·귀국일 또는 현지 이용일, 박·일, 주요 동선, 이동 시간, 집결·픽업 |
| 가격 | 통화, 금액, 성인/아동, 객실 조건, 인원, 출발일, 옵션, 유류할증·세금 포함 여부, 조회 시각 |
| 포함/불포함 | 항공·호텔·식사·차량·입장료·보험, 필수 팁, 선택관광·쇼핑 횟수, 1인실 비용 |
| 운영 | 최소 출발 인원, 출발 확정, 예약 가능 여부, 이용 연령, 보행·접근성 조건 |
| 취소 | 약관 원문/출처, 기준 시간대, 취소 시점별 조건. 불명확하면 요약하지 않고 확인 필요 |
| 출처 | 필드별 sourceId, 원문 위치/짧은 발췌, 확인 상태, checkedAt |
| 이미지 | 파일, 권리 상태 `owned / licensed / unknown`, 출처와 사용 범위 |

금액은 최소 통화 단위의 정수로 저장한다. 서로 다른 통화는 환산 근거 없이 총액을 더하지 않는다. 한 상품의 출발일 조건을 다른 상품으로 전파하지 않는다. `노쇼핑`, `노옵션`, `노팁`은 각각 독립 필드이며 제목만으로 추정하지 않는다.

출처 상태는 `verified / unverified / conflict / missing`이다. URL이 있다는 이유만으로 verified로 만들지 않는다. 사용자가 원문과 필드의 대응을 검토하거나, 어댑터가 해당 필드의 추출 근거를 보존한 경우에만 확인 상태를 올린다. 확인된 것은 원문에 대한 대응이며 미래 가격을 보장하는 뜻은 아니다.

### 5.3 갱신과 링크 보존

- 가격·재고·혜택·판매 상태·출발 확정은 마지막 확인 후 24시간을 재확인 기본 주기로 삼는다. **앱의 초기 운영값이며 네이버 규정이 아니다.** 발행 직전 재확인을 요청하고 확인할 수 없으면 정확한 가격·마감 표현을 제외한다.
- 취소·포함 조건도 발행 직전 현재 선택 옵션과 대조한다. 원고가 사용하는 필드의 출처가 바뀌면 해당 원고를 다시 review로 만든다.
- 제휴 링크에 UTM을 추가하거나 쿼리 제거·정렬·인코딩 재작성·임의 단축을 하지 않는다. 저장한 원문을 그대로 출력하고, 최종 URL을 equality 검사한다. 앞뒤 입력 공백만 제거한다.
- 일반 상세 URL과 제휴 URL은 별도 필드다. 짧은 링크의 리다이렉트 목적지를 조사에 읽을 수 있어도 그 목적지로 출력 링크를 대체하지 않는다.
- 채널별 발급 링크가 공식적으로 지원되고 사용자가 실제 발급한 경우에만 별도 저장한다. 내부 campaignId는 링크 밖에서 관리한다.
- 과거 특가나 대표 최저가는 모든 날짜의 예약가로 쓰지 않는다. 확인 시각·출발일·객실·인원 조건을 본문에 함께 표시한다.

## 6. 원고 생성과 채널별 변환

### 6.1 공통 브리프

`주 키워드 1개 + 대상 독자 + 선택 상품/옵션 + 해결할 질문 3~5개 + verified 사실 목록 + 불확실 항목 + 실제 경험 입력 + 이미지 목록 + 고지/링크 정책`을 작성한다. 각 상품 주장에 claimId와 sourceId를 붙여 채널 변환까지 추적한다.

첫 구현은 기존 검색 브리프에 상품 근거·필수 답변을 보강하고 기존 블로그 생성기를 호출한다. 후속 SNS 확장에서는 공통 근거에서 문안을 생성한다. SNS에 사용된 주장 집합은 승인된 브리프의 부분집합이어야 하며 요약하면서 가격·취소 조건을 없애지 않는다.

### 6.2 블로그 원고

기본 글 유형은 `예약 전 체크`, `상품 조건 비교`, `대상별 선택 가이드`, `확인된 실제 경험` 네 가지다. 비교형만 상품 2~3개를 받는다. 후기형은 사용자가 직접 경험한 상품·날짜·내용을 입력한 경우에만 허용한다.

권장 구성:

1. 경제적 이해관계 고지.
2. 이 글이 답하는 질문과 누구에게 필요한지.
3. 선택 기준: 추가 비용·이동 부담·자유시간 등.
4. 상품 조건표: 날짜·인원·객실·포함/불포함·취소 기준.
5. 적합한 경우와 주의할 경우, 근거 있는 차이.
6. 실제 자료에서 나온 FAQ 3~5개. 공식 답을 못 찾으면 판매사에 확인할 질문으로 표시.
7. 현재 조건·예약 가능 여부 확인 CTA. 선택 상품별 링크는 한 번씩.
8. 확인 시점과 출처.

기본 분량은 1,800~2,600자 제안값이고 사용자가 조정한다. 분량·키워드 반복 횟수를 순위 규칙으로 설명하지 않는다. 제목 후보 3개 중 조건과 실제 내용을 맞춘 1개를 선택한다. `최저가`, `출발 확정`, `마감 임박`, `무조건 추천`은 확인된 근거 없이 쓰지 않는다.

### 6.3 Threads·X 문안 — 후순위, 첫 구현 제외

| 채널 | 기본 산출물 | 문장 흐름 | 검증 |
|---|---|---|---|
| Threads | 고민 공감형 1개 + 체크리스트형 1개 | 질문 → 선택 기준 2~3개 → 확인된 핵심 → 링크 안내 | 고지 포함 500자 이내의 짧은 본문 프로파일 |
| X | 질문형 1개 + 조건 요약형 1개 | 핵심 질문 → 결정 기준 1~2개 → 확인 링크 | twitter-text 가중 길이 280 이내 |

채널별 말투만 조정하고 새로운 가격·체험·할인·긴급성을 추가하지 않는다. Threads를 잘라 X에 넣지 않는다. 고지를 먼저 확보한 뒤 남은 분량 안에서 본문을 작성한다. 자동 문자열 절단으로 고지·링크·조건을 잃지 않도록 의미를 줄여 재작성한다.

SNS 링크 모드:

- `blog`: 발행한 블로그 URL로 안내하는 문안. 발행 전에는 자리표시자를 결과 미리보기에만 보여주고 복사 완료 상태로 만들지 않는다.
- `affiliate`: 채널 정책 검토 결과가 allowed이며 해당 발급 링크가 확인된 경우 원문 삽입.
- `none`: 링크 없이 정보 문안으로 저장. 제휴 완료 원고와 구분.

SNS 홍보 문안의 첫 부분에 같은 경제적 이해관계 고지를 유지한다. SNS 채널 정책이 unknown이면 문안 생성은 가능하되 제휴 링크 포함 외부 사용 상태는 review다. 금지 채널이면 해당 제휴 링크 결과는 hold다. 광고 표시를 본문 밖 댓글 하나에만 두는 흐름을 기본값으로 삼지 않는다.

### 6.4 이미지

직접 촬영 또는 사용권이 확인된 상품 이미지·지도·조건표를 사용한다. 권리 상태 unknown 이미지는 내보내기에서 제외한다. 공급사 이미지라는 이유만으로 제휴 사용권이 있다고 가정하지 않는다. 조사용 화면 캡처와 발행용 이미지 사용권은 별개다. 기존 뉴스 이미지 자동 수집·워터마크 제거 안내를 여행 탭에 연결하지 않는다.

## 7. 검수와 상태 전이

`ready`는 현재 입력·근거 기준으로 편집기에 전달 가능한 상태이며 예약 가격이나 수익을 보증하는 표시가 아니다. `review`는 사람이 확인할 항목이 남은 상태다. `hold`는 제휴 원고의 외부 사용을 막는 상태다. 보류 원고도 로컬 보관한다.

| 문제 | 상태와 동작 |
|---|---|
| 가격·출발일·취소·포함 조건이 근거와 충돌 | hold. 충돌 해결 전 해당 채널 복사·에디터 전달 차단 |
| 고지 누락, 발급 링크 변형, 미지원 유형의 제휴 추천 | hold. 고지·링크는 모델 출력에 맡기지 않고 코드에서 구성 |
| 입력하지 않은 직접 이용·내돈내산·후기·사진 경험 | hold. 허위 경험 문장 제거 후 재검수 |
| 선택 옵션의 가격 확인이 24시간 경과·누락·미래 시점 | hold. 등록 상품에서 근거와 가격을 재확인한 뒤 재검수. 24시간은 앱 운영값이며 네이버 정책 기간이 아님 |
| 상품 조건 일부 미확인 | review. 그 조건을 추천 근거로 사용하지 않음 |
| SNS 문안 길이 초과 | 그 채널 hold. 정상 블로그 결과는 보관 가능 |
| 이미지 권리 unknown | 이미지 제외, 원고는 review. 사용 가능 이미지가 없어도 텍스트 초안 생성 가능 |
| 수집 차단·로그인 요구·지원하지 않는 구조 | 자료 부족으로 표시, 기존 입력 보존, 허위 데이터로 보충하지 않음 |

생성 → 수동 수정 → 상품 갱신 → 링크 모드 변경 → 외부 전달 직전에 모두 같은 검수 함수를 실행한다. 블로그 결과가 ready여도 SNS 결과를 자동 ready로 승격하지 않는다. 실패한 채널만 재생성하며 제품 사실은 공통 브리프에 고정한다.

## 8. 기존 프로젝트에 적용할 구조

조사 당시 실제 코드를 읽은 결과:

| 파일 | 현재 확인한 특징 | 적용 결정 |
|---|---|---|
| `app/app.html` | 사주·무주 준비 중·구버전 탭. 사주 UI 이벤트에 `saju` 하드코딩 다수. 현재 사용자 수정 존재 | 여행 패널과 JS는 별도 파일로 추가하고 공통 탭 선택만 최소 수정 |
| `src/topics/index.js` | 사주와 비활성 무주 등록 | 여행 주제 metadata 등록 |
| `src/topics/topicContext.js` | 서비스 운영자 고지, 사주 기본 문구, 무료→유료 CTA, UTM 추가 | 여행에 그대로 재사용하지 않고 여행 전용 context 사용 |
| `electron/main.js`의 `runTopicGeneration` | 검색은 daily, 홈판은 saju 경로. 정적 상품 목록·사주 검수에 의존 | 주제별 분기에서 여행 맥락·검수 어댑터를 호출하고 기존 검색 생성기로 연결 |
| `src/topics/drafts.js` | 원고 보관은 공통이고 result 객체를 저장, 최대 200개 | 기존 topicId 필터와 result에 제휴 맥락·상품 스냅샷을 저장. 기존 파일 재사용 |
| `src/keyword/report.js` | XLSX 파싱, `<10`·결측 처리 제공. 분류·선정은 사주 규칙 포함 | 파싱을 재사용하고 여행 분류는 분리 |
| `src/keyword/integratedSerp.js` | 실제 통합검색 관찰·차단 보호 연계 | 호출 주입 방식으로 재사용, 실패 상태 보존 |
| `src/generator/generateSearchPost.js`, `runClaude.js`, `factCheck.js` | 검색 생성 파이프라인·모델 호출·원문 대조 | 생성 파이프라인 재사용, connectContext가 있을 때 상품 근거와 필수 답변 보강 |
| `src/topics/editorDelivery.js` | 기존 finishGen 연결 | ready와 명시적 사람 검수 후 review 전달에 재사용. hold는 차단하고 최종 링크 보존 검증 추가 |
| `src/performance/tracker.js` | 검색 순위·발행 주소·조회수 기록 | 기존 블로그 성과 항목 재사용. 제휴 실적은 후속 옵션 |
| `app/app.html`의 `affiliateDisclosure` | 제목·키워드의 여행/캠핑 단어로 여행·쇼핑 고지를 추정 | 신규 탭은 connectKind 명시값으로 고지를 선택. 캠핑용품을 여행으로 오분류하지 않음 |
| `scripts/check.js` | 인라인 스크립트와 IPC 점검, 외부 UI 파일의 window.api 사용은 점검하지 않음 | 여행 외부 JS의 브릿지 사용도 검사하도록 확대 |

추가 모듈은 `src/connect/` 아래 상품 근거·제휴 정책·여행 상세·키워드 매칭·추가 검수로 좁힌다. `src/generator/`와 `src/topics/`의 기존 생성/보관 동작을 확장하며 `src/travel/generate.js`, 별도 여행 drafts/metrics 저장소는 만들지 않는다. UI는 `app/travel-connect.html/js/css`로 분리하고 기존 메인 화면의 주제 탭과 연결한다.

HTML 조각은 로컬 파일만 로드하고 스크립트는 명시적으로 포함한다. 임의 외부 HTML·상품 설명은 텍스트로 표시하고 렌더러에 Node/fs 권한을 노출하지 않는다. main/preload 브릿지 검증은 기존 패턴을 따른다.

신규 상품/출처/설정만 `%APPDATA%/blog-auto/connect/` 아래 버전 있는 JSON·원자적 쓰기로 저장한다. 원고는 기존 `topic-drafts.json`, 프로필은 `topic-profiles.json`, 블로그 성과는 기존 저장소에서 topicId로 구분한다. 기존 항목을 덮어쓰거나 초기화하지 않는다. 기존 보관함의 200개 제한으로 여행 원고 추가가 사주 원고를 자동 밀어내지 않도록 제휴 등록 경로는 용량 초과를 알리고 저장을 거부한다.

원고에는 생성 당시 상품 스냅샷·상품/옵션 id·확인한 사실과 출처 id·정책 버전을 저장한다. 오래 보관한 원고를 내보낼 때 현재 상품과 대조한다. 링크 원문·계정 토큰은 일반 로그에 남기지 않는다.

## 9. 성과 기록과 운영

첫 구현은 기존 블로그 발행 URL·선정 키워드·상품/옵션·생성 버전을 연결하고 기존 조회·검색 노출을 추적한다. 별도 제휴 실적 대시보드와 SNS 연결은 후순위다. 아래 제휴 실적 설계는 그 확장 시 적용한다.

초기에는 공식 대시보드 자료를 수동 입력하고, 파일 내보내기 형식이 실제 확인된 경우에만 CSV/XLSX 가져오기를 추가한다. 날짜·지표명·집계 단위·실적 상태를 보존한다. 앱의 복사 횟수·에디터 전달 횟수를 상품 클릭·예약으로 계산하지 않는다.

공식 데이터가 상품/링크 단위만 제공되면 채널별 실적으로 임의 배분하지 않는다. 최근 클릭 기준·다른 대상 상품 예약 가능성 때문에 소개 상품의 매출과 링크 실적은 일치하지 않을 수 있다.

검수 시간, 사실 오류 수정 건수, 생성 성공률, 블로그 노출, 링크 유입(공식 자료가 있을 때), 예약·취소·확정 수익을 기록한다. CTR/CVR/EPC는 분자·분모가 같은 기간·집계 범위일 때만 계산하고, 공식 자료에 클릭 수가 없으면 EPC를 만들지 않는다.

기본 운영은 한 지역·한 독자층에서 검토한 상품 5~10개로 시작해 원고 10편을 검수하는 방식이다. 이는 시험 운영 제안이며 수익 예측이나 통계적으로 충분한 표본이라는 뜻은 아니다. 동일 글에서 제목만 바꾸는 양산보다 새로운 질문·상품 조건·실제 경험의 차이를 기록한다.

## 10. 단계와 공수 제안

| 단계 | 완료되는 기능 | 개발·검증 공수 추정 |
|---|---|---|
| 1. 기반 | 기존 탭 연결·상품/출처 등록·제휴 구분·링크 보존 | 2~3 개발일 |
| 2. 조사·기획 | 기존 XLSX·자동완성·검색 관찰 연결·상품 매칭 | 2~3 개발일 |
| 3. 생성·검수 | 기존 검색 생성기·보관함·에디터 확장·여행 조건 검수 | 3~4 개발일 |
| 4. 시험 운영 | 실제 상품 대조·화면 확인·기존 경로 회귀 검증 | 1~2 개발일 |

합계 8~12 개발일을 수정 추정으로 잡는다. SNS 생성·수집, 쇼핑 전용 탭 추가, 별도 제휴 실적 대시보드, 공급사 자동 수집·예약 발행은 포함하지 않는다. 재사용 접점 검증 결과에 따라 공수를 조정한다.

개발 순서는 **상품 사실·링크 모델 → 조사·브리프 → 검색 블로그 생성·검수 → 화면 연결·성과**다. 다중 채널은 후속 범위다. 위 공수는 설계 시 추정이며 실제 완료 여부와 검증 결과는 프로젝트 상태 문서에서 관리한다.

## 11. 검증 기준

- 유효 제휴 링크가 저장·수정·생성·복사·에디터 전달에서 원문과 동일하다.
- 출발일·인원·객실 조건이 다른 가격을 같은 조건으로 비교하지 않는다.
- 상품 근거 충돌, 고지 누락, 허위 경험, 미지원 상품은 외부 전달이 차단된다.
- 첫 구현에는 SNS 의존성이 없고 기존 블로그 출력 형식을 그대로 사용한다. SNS 확장 때 가격 조건·고지·채널 길이 검증을 추가한다.
- 기존 사주·구버전 탭·예약 경로·프로필 데이터가 회귀 테스트를 통과한다.
- 차단·로그인·수집 실패를 빈 결과와 구별하고 사용자가 입력한 자료를 보존한다.
- 원고를 수정하거나 상품 조건을 갱신하면 채널별 재검수가 실행된다.
- 공식 실적 자료에 없는 클릭·채널별 예약·확정 수익은 생성하지 않는다.

상세 파일·인터페이스·테스트 순서는 [구현 계획](../superpowers/plans/2026-10-07-travel-connect-tab-plan.md)에 정리했다.
